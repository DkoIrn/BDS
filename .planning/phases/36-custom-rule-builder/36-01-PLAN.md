  <name>Task 1: Database migration, Pydantic models, and rule execution engine</name>
  <files>supabase/migrations/20260416_custom_rules.sql, backend/app/models/schemas.py, backend/app/services/custom_rules.py, backend/tests/test_custom_rules.py</files>
  <behavior>
    - Test: threshold rule (column > 100) flags rows where column exceeds 100
    - Test: comparison rule (colA > colB) flags rows where colA exceeds colB
    - Test: null_check rule (is_null) flags rows with missing/empty values
    - Test: AND group with 2 conditions only flags rows matching both
    - Test: OR group with 2 conditions flags rows matching either
    - Test: nested group (depth 2) evaluates correctly
    - Test: nesting depth > 2 raises ValidationError
    - Test: empty group returns no matches (fail-safe)
    - Test: missing column returns no matches (not crash)
    - Test: execute_custom_rule produces ValidationIssue dicts with correct fields
  </behavior>
  <action>
    1. Create Supabase migration `supabase/migrations/20260416_custom_rules.sql`:
       - `custom_rules` table with columns: id (UUID PK), profile_id (FK to validation_profiles ON DELETE CASCADE), user_id (FK to auth.users ON DELETE CASCADE), org_id (FK to organisations ON DELETE CASCADE), name (TEXT NOT NULL), description (TEXT DEFAULT ''), severity (TEXT CHECK IN critical/warning/info DEFAULT 'warning'), rule_definition (JSONB NOT NULL), enabled (BOOLEAN DEFAULT true), created_at, updated_at
       - Index on profile_id and org_id
       - RLS enabled with 4 policies: org members SELECT, reviewers/admins INSERT, owner UPDATE, owner/admin DELETE
       - updated_at trigger using existing handle_updated_at()

    2. Add Pydantic models to `backend/app/models/schemas.py`:
       - `Condition(BaseModel)`: column (str), rule_type (Literal["threshold", "comparison", "null_check"]), operator (str), value (float | str | None = None), compare_column (str | None = None)
       - `ConditionGroup(BaseModel)`: logic (Literal["AND", "OR"] = "AND"), conditions (list[Condition] = []), groups (list["ConditionGroup"] = [])
       - `CustomRuleDefinition(BaseModel)`: name (str), description (str = ""), severity (Literal["critical", "warning", "info"] = "warning"), root_group (ConditionGroup)
       - Add @model_validator to CustomRuleDefinition that validates nesting depth <= 2

    3. Create `backend/app/services/custom_rules.py` with three functions:
       - `evaluate_condition(df, cond)` -> pd.Series boolean mask. Handle threshold (pd.to_numeric + operator map), comparison (pd.to_numeric both columns + operator map), null_check (isna + empty string check). Return False mask if column missing.
       - `evaluate_group(df, group)` -> pd.Series. Recursively combine condition masks and sub-group masks using AND/OR logic. Return False mask if no conditions/groups.
       - `execute_custom_rule(df, rule, kp_column=None)` -> list[ValidationIssue]. Evaluate root_group, iterate flagged rows, produce ValidationIssue dicts with rule_type="custom_rule", message="Custom rule '{name}' triggered", severity from rule. Include kp_value if kp_column exists.

    4. Write tests in `backend/tests/test_custom_rules.py` covering all behaviors listed above. Use small DataFrame fixtures (5-10 rows). Test the execution engine functions directly, not via API.
  </action>
  <verify>
    <automated>cd backend && python -m pytest tests/test_custom_rules.py -x -v</automated>
  </verify>
  <done>All 10+ test cases pass. Migration SQL is valid. Pydantic models validate nesting depth. Rule executor handles all three rule types with AND/OR grouping and produces standard ValidationIssue dicts.</done>
