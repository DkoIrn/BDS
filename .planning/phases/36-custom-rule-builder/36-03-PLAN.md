  <action>
    **1. Next.js API proxy routes** (follow existing pattern from src/app/api/validate/route.ts):

    - `src/app/api/rules/route.ts`: POST (create) and GET (list by profile_id query param) -- proxy to FastAPI /api/v1/rules/
    - `src/app/api/rules/[ruleId]/route.ts`: PUT (update) and DELETE -- proxy to FastAPI /api/v1/rules/{ruleId}
    - `src/app/api/rules/test/route.ts`: POST -- proxy to FastAPI /api/v1/rules/test. Request body includes rule_definition and dataset_id.

    All proxies: extract auth from Supabase session, forward to FASTAPI_URL, return JSON response. Follow same error handling pattern as existing validate route.

    **2. Server actions** (`src/lib/actions/custom-rules.ts`):
    Follow pattern from `src/lib/actions/profiles.ts`:
    - `getRulesForProfile(profileId: string)`: fetch GET /api/rules?profile_id={id}, return CustomRule[]
    - `createRule(profileId: string, rule: CustomRuleDefinition)`: POST /api/rules with profile_id + rule fields, return CustomRule
    - `updateRule(ruleId: string, updates: Partial<CustomRuleDefinition & {enabled: boolean}>)`: PUT /api/rules/{ruleId}
    - `deleteRule(ruleId: string)`: DELETE /api/rules/{ruleId}
    - `testRule(ruleDefinition: ConditionGroup, datasetId: string, severity?: string)`: POST /api/rules/test, return RuleTestResult

    Note: Server actions call the Next.js API proxy routes (not FastAPI directly). Use the same fetch pattern with cookies forwarding as existing actions.

    **3. RuleTestPreview component** (`rule-test-preview.tsx`):
    Props: `result: RuleTestResult`
    Display: Card with:
    - Summary line: "{matching_rows} of {total_rows} rows matched" (bold matching_rows, use text-destructive if > 0, text-emerald-600 if 0)
    - If truncated: warning badge "Dataset was truncated to 10,000 rows for preview"
    - If sample_matches.length > 0: collapsible table showing first 50 matching rows with row_number and column values
    - If matching_rows === 0: muted text "No rows matched this rule"
    Uses shadcn Card, Table (if available) or simple div grid.

    **4. Stage-validate integration:**
    Add custom rules section to stage-validate.tsx:
    - Below the existing profile selection, add a "Custom Rules" section with violet accent
    - Show a list of saved rules for the current profile (fetch via getRulesForProfile when profile is selected)
    - Each rule row: name, severity badge, enabled toggle, edit button, delete button
    - "Add Custom Rule" button opens the RuleBuilder component (from plan 02) in an expandable section or dialog
    - When user clicks "Test Rule" in RuleBuilder: call testRule() with the current dataset_id from pipeline state, display result via RuleTestPreview
    - When user clicks "Save Rule" in RuleBuilder: call createRule() with the selected profile_id, refresh rules list, show success toast
    - Column options for RuleBuilder: derive from current columnMappings (map each mapping to {value: mappedType, label: originalName})
    - Pass custom_rule_ids (enabled rule IDs) to the validation request when user runs validation

    **5. Backend pipeline integration:**
    - In `backend/app/models/schemas.py`: add `custom_rule_ids: list[str] | None = None` to ValidateRequest
    - In `backend/app/services/validation.py` or the background task that calls run_validation_pipeline: after built-in checks complete, if custom_rule_ids provided, query custom_rules table for those IDs where enabled=True, parse each rule_definition as CustomRuleDefinition, call execute_custom_rule for each, extend all_issues with results
    - In `src/app/api/validate/route.ts`: forward custom_rule_ids from request body to FastAPI

    **Important:** Custom rule issues use rule_type="custom_rule" and appear in the standard triage/inspect view because they are standard ValidationIssue objects. No triage UI changes needed.
